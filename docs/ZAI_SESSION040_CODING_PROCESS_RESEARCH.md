## Executive summary

Three findings from Sessions 037–039 frame this document: (1) a deterministic controller around the frozen 0.5B more than doubles its unassisted score (037: A 4/15 vs B 9/15; stable at B 9/15 on a fresh suite in 038A); (2) an execution-feedback repair loop did **not** beat single-shot contract-first (038A: R 8/15, McNemar p = 1.0) — the real gaps (routes 1/12 both tracks, demo-vocabulary copying, relation-side optionality) are generation-shape failures feedback cannot fix, and FIM cannot rewrite; (3) the 037 invariant "token cap" was an evaluator artifact (2/3 invariants solved on attempt 1 in 27–70 tokens) — several past failures were harness defects, not model limits. Each of the eight techniques below gets: literature basis; honest 0.5B/~2k-context applicability separating *controller* gains from *model* gaps; a concrete repo design; a Session-040 measurement plan with falsification criteria; a grounded expected-effect rating. Bottom line: contract-first, structured error diagnosis, execution-feedback repair, and context retrieval lead on expected effect × cost; FIM and persistent memory rank last. Session 040 measures the **ceiling of controller assistance** on the 18 dev contracts and the residual gap profile that only weight-level work (a future, separately-authorized session) could close.

## 1. Contract-first development

**(a) Research basis.** Spec-before-implementation is the core of Meyer's Design-by-Contract, of test-first practice (Beck's TDD), and of contract-first API development (OpenAPI/JSON Schema before handlers). QuickCheck-style property testing (Claessen & Hughes 2000) shows executable specs catch what type checks cannot; SWE-bench (Jimenez et al. 2024) and SWE-agent (Yang et al. 2024) score agents against specs plus hidden tests — the spec is ground truth, not code shape. For a weak model, a machine-checkable contract turns "write a route" into constrained generation with an objective oracle.

**(b) Applicability at 0.5B.** The one technique with direct in-repo causal evidence: 037 A 4/15 → B 9/15, reproduced at 9/15 on a fresh suite (038A). Mechanism: constraint narrowing — the contract's export shape, route path, envelope, and status default keep greedy decoding inside the target structure. Even with a perfect contract the model cannot do multi-branch POST validation (FK lookup + duplicate check) or GET `where`-construction; and 039 found Prisma SQLite rejects `mode: "insensitive"`, so the `LOWER()` convention must be *stated in the prompt* — part of the contract surface. Contract-first is substantially **controller-side**: the controller authors contract and oracle; Track-A movement under prompt deltas measures elicitation, not capability.

**(c) Concrete design.** Standardize what exists: (i) freeze the Track-B template in `archagent/z040/prompts.py` — contract JSON (public requirements only), target file name, export-shape declaration, conventions block (`LOWER()` search, v2's `status String @default("<initial>")`, import redirection to `@/lib/db`), pinned doc excerpts — all inside the 033 allowlist (public contract, model's own previous bytes, public execution feedback, concept explanations, pinned docs; never teacher code); (ii) demos domain-disjoint from all 16 v2 domains, or abstract concept explanations (or-stage lesson); (iii) budget: single-shot at the 038A 520-token cap inside the shared 2,000-token budget, blind ladder ≤ 6 attempts, structural gate only in-loop; (iv) layout: `experiments/z040-coding-process/tracks/B/<task>/`, per-attempt generations archived.

**(d) Measurement.** B vs A on the 18 dev contracts, per-skill deltas across the six v2 skills. **Falsification:** B − A ≤ 0 overall; the delta vanishes under a length-matched non-contract control (context length, not contract content); or gains concentrate where A already partially succeeds.

**(e) Expected effect: LARGE** — the only replicated, paired, fresh-suite effect at this scale; residual uncertainty is family coverage (routes), not the average effect.

## 2. Breaking complex tasks into manageable components

**(a) Research basis.** Decomposition underpins prompt-based planning: chain-of-thought (Wei et al. 2022), least-to-most prompting (Zhou et al. 2023), plan-and-solve (Wang et al. 2023). Agent scaffolds agree: SWE-agent (Yang et al. 2024) found a simplified, well-chunked agent–computer interface beats richer raw ones; AlphaCode (DeepMind 2022/2023) decomposes into generate–filter–validate stages.

**(b) Applicability at 0.5B.** The controller *already* decomposes — Curriculum v2's six skills and the per-piece pipeline (schema → invariant → routes → UI) are controller-side decomposition, embedded in the 9/15 baseline. Track D tests *model-visible* decomposition: whether an ordered sub-piece plan for a POST handler (signature → parse/validate → FK/duplicate checks → persistence/response) yields more complete handlers than one monolithic prompt. At ~2k effective context the risk is inversion: sub-piece prompts lose the global context keeping pieces consistent, and 037's engine tracks (C 6/15, D 6/15 with *fewer* tokens, 7,078/6,696 vs B's 20,170) showed more machinery can reduce passes while improving token economy. For routes the sign is unknown; evidence is absent — exactly what Track D measures.

**(c) Concrete design.** Plans are controller-authored templates per skill family, frozen in `archagent/z040/prompts.py` (not model-generated — 038A logged near-empty decompose outputs). Each sub-piece is generated, installed, structurally gated, then the next, with the model's own prior sub-piece bytes in context (allowlist-compliant cross-piece context). Budget: the same 2,000/6 per piece partitioned across sub-pieces (e.g., 4 × ≤500 tokens), logged per sub-piece so D vs B is efficiency-comparable. FIM (§3) is the natural insertion mode; install order goes in the per-task ledger (QWEN-ORIGINAL per span).

**(d) Measurement.** D vs B on dev, per-skill, tokens-per-pass raw and budget-normalized. **Falsification:** D ≤ B overall; D > B only with token overhead exceeding budget (efficiency-normalized gain ≤ 0); or D gains appear only where B already passes (redistribution, not expansion).

**(e) Expected effect: SMALL-to-MEDIUM, uncertain sign** — the controller half is banked in the baseline; the model-visible half fights context fragmentation at 2k, with 037's engine as the cautionary prior.

## 3. Native fill-in-the-middle (FIM) completion

**(a) Research basis.** FIM was introduced by Bavarian et al. 2022 ("Efficient Training of Better Coding Language Models"): a pretraining document transform (PSM/SPM, ~50% of documents) yields infilling conditioned on prefix and suffix at no left-to-right cost. Production inline completion (Copilot-style) uses it for *local, additive* edits — inserting a body between anchors. Qwen2.5-Coder is trained with FIM support (`<|fim_prefix|>`, `<|fim_suffix|>`, `<|fim_middle|>`), a native capability of our checkpoint.

**(b) Applicability at 0.5B.** 038A is unusually specific: `ma-booking`'s sole defect was relation-side optionality (`berthId String?` correct; `berth Berth` missing `?`), and FIM micro-repair could not fix it — 13-token duplicates, flat, stopped at 917/2,000 tokens — while blind resampling hit the correct form on attempt 4. **FIM cannot rewrite; it can only insert.** Its realistic role is extension, not repair: appending a branch inside the model's own verified handler, or filling a scaffold region. Filling a *trusted* scaffold mixes teacher anchors with model bytes — 033 per-file attribution needs a per-span extension, and permissibility is a governance question.

**(c) Concrete design.** `archagent/z040/fim.py`: format `<|fim_prefix|>{prefix}<|fim_suffix|>{suffix}<|fim_middle|>`, greedy decoding, caps identical to Track B. Sanctioned: (1) *self-extension* — prefix = the model's own installed verified bytes, suffix = the file's closing anchor, middle = the requested addition; (2) sub-piece insertion under Track D. Prohibited: semantic repair of existing model bytes (`ma-booking`) — Track C uses full-context regeneration. FIM tokens count against the piece budget; same gates and final scoring.

**(d) Measurement.** Paired on dev: FIM vs left-to-right on extension-shaped sub-tasks ("add a combined-filter branch to your verified GET handler"), same seeds/budget. **Falsification:** no pass-rate difference; or FIM anchor-echoes duplicates at a higher rate than rewrite mode (confirming permanent insertion-only restriction).

**(e) Expected effect: SMALL** — direct negative evidence for repair; none yet for extension (must be measured). Cheap (a prompt-format change), and Track D needs an insertion primitive.

## 4. Execution-feedback-guided repair

**(a) Research basis.** Self-Debugging (Chen et al. 2023) showed iterative repair from execution results helps, most when feedback includes explanations rather than raw traces; Reflexion (Shinn et al. 2023) adds verbalized reflection persisted across attempts. Execution also works as a selection signal: CodeT (Li et al. 2022) selects via code/test agreement; AlphaCode filters on example tests. General pattern in the literature: self-repair gains shrink as models get smaller and feedback noisier; weak models loop rather than converge.

**(b) Applicability at 0.5B.** 038A is the decisive local experiment: Track R 8/15 vs B 9/15, McNemar p = 1.0, with 9% fewer loop tokens (not a budget artifact). Anatomy: (i) routes fail at generation shape before any probe runs — feedback has nothing to act on (037's C/D); (ii) demo-vocabulary copying yields a well-formed predicate with wrong domain words that counterexample feedback cannot fix (dedup spiral); (iii) optionality near-misses need a *rewrite*, which FIM cannot do. Honest conclusion: at 0.5B feedback repair converts **near-misses with precise counterexamples** and nothing else; 038A's suite held few such near-misses (its one was FIM-trapped). Controller benefits (early stop, token savings) are real but controller-side.

**(c) Concrete design.** Track C = 038A Track R semantics plus the upgraded feedback block produced by diagnosis (§5): `class` (syntax | structural | behavioral | timeout | no_verdict), `gate` (evaluator/case id), `observed` (minimized counterexample: inputs + actual status/body), `expected` (contract clause id + required value), `diff-hint` (line/char span only; never corrected code — 033 allowlist). Repair prompt = Track-B prompt + model's own previous bytes + feedback block; full-context regeneration for semantic edits; dedup-stop retained (flat/duplicate → stop, 038A). Budget: 2,000/6 with per-repair-attempt token logs. React/integration repair requires the two missing 039 evaluators (§7) — Track C runs first on the four evaluator-backed skills.

**(d) Measurement.** (i) Final C vs B (replication on v2 dev). (ii) **Repair-attempt efficiency** (the isolating metric): pieces recovered per repair attempt; first-repair success rate; tokens per repaired piece; plus the critical control — *budget-matched blind resampling*: C's loop vs B spending the same tokens on unconditional resampling. **Falsification:** C ≤ B on final score AND repair-recovery ≤ resampling-recovery at equal budget (feedback adds nothing over more sampling); or all C gains are on structural near-misses (a near-miss converter, full stop).

**(e) Expected effect: SMALL on final score** (replicated null; the v2 route-heavy mix is unfavorable), **MEDIUM on near-miss conversion** if minimized counterexamples work — that claim has no direct evidence yet and must be measured, not assumed.

## 5. Structured error diagnosis

**(a) Research basis.** The software-engineering half of self-repair is fault localization and triage: knowing *what class* of failure occurred before choosing a fix. Self-Debugging found "rubber-duck" explanation helps mainly by classifying the fault; SWE-agent attributes much of its gain to a tight, predictable interface for *observing* state rather than smarter edits; LEAP-style work (distilling mistakes into short in-context principles) shows failures become reusable only when first named and categorized.

**(b) Applicability at 0.5B.** Mostly controller-side — and that is its value. The model cannot be trusted to diagnose, but it benefits from receiving a diagnosis it can act on. The 037/038A postmortems price the alternative: 2/3 of the "invariant gap" was misdiagnosed for a session (tri-state `bool(None)` + double-emit masking); 037's engine burned structural-only loops on pieces that could never pass probes. Diagnosis also protects budgets: no_verdict (harness bug — halt, log, fix) vs fail (candidate defect — feed back) vs syntax (regenerate, do not probe) prevents the discarded-solution and dedup-spiral modes. One model-side test: a repair prompt that *states the fault class and violated clause* measures whether the model maps a named fault to a fix — a minimal form of error understanding.

**(c) Concrete design.** `archagent/z040/diagnosis.py`, a deterministic triage cascade on every candidate before any model-facing decision: (1) syntax gate (TypeScript parse) → syntax; (2) structural gate (export shape, 039 candidate hygiene) → structural; (3) behavioral probes (039 evaluators: invariant seeded+single-verdict fuzz; GET/POST runner with reseeded fixtures, 10 s timeout, import redirection) → behavioral with per-case ids; (4) no-verdict capture → harness-bug path (halt, never reject, never pass). Output: the §4 feedback block plus a *minimized* counterexample (inputs shrunk to the smallest reproducing form — deterministic, controller-side). All verdict parsing inherits 039's single-verdict fail-closed contract; no_verdict ≠ pass everywhere.

**(d) Measurement.** A/B inside Track C: classified+minimized vs raw case-table feedback (same pieces, seeds, budget). Metrics: first-repair success rate, convergence depth, wasted attempts (attempts on unrepairable classes — should drop when diagnosis reroutes them). **Falsification:** classified/minimized feedback does not improve first-repair success; or early-stop saves tokens with flat final score (controller-only benefit — report as such).

**(e) Expected effect: MEDIUM controller-side, SMALL model-side** — grounded in 038A forensics (pieces lost or spun on verdict-class confusion that triage prevents); the model-side gain is untested.

## 6. Retrieval of relevant project context

**(a) Research basis.** Repository-level completion (e.g., RepoFusion, Shrivastava et al. 2023) shows retrieving the right cross-file context — imports, sibling modules, conventions — substantially improves completion over file-local context; production assistants do exactly this. The negative corollary matters equally: retrieved *examples* induce copying — the nearest-neighbor temptation — the 038A demo-vocabulary failure generalized.

**(b) Applicability at 0.5B.** At ~2k effective context, retrieval is the *only* way the model sees anything beyond the contract (the controller already does it implicitly via pinned docs). The open question is what to retrieve for routes: (i) the task's own verified schema bytes (own previous bytes — allowlist-compliant), (ii) the pinned conventions block (`LOWER()`, import shape, envelope), (iii) *abstract* handler-shape explanations rather than concrete sibling handler code — concrete cross-domain code is outside the 033 allowlist *and* the documented cause of vocabulary copying (`or-stage`: demo's `raw→edited→published` instead of the task's `growing→ripe→picked`). Retrieval is a controller technique with a leakage-shaped blast radius: concreteness buys structure and costs domain fidelity. The model must still map the task's own domain nouns into code itself; the vocabulary lock only detects failures.

**(c) Concrete design.** `archagent/z040/retrieval.py`, deterministic (no embeddings — nothing stochastic enters prompts): a per-piece context assembler with a fixed slot budget (~60% of the 2k window) — slot 1 contract JSON (always); slot 2 conventions block (routes always); slot 3 the model's own verified pieces from the same app (schema when generating routes; schema+GET for integration); slot 4 pinned doc excerpts (Prisma `where`/`include`, handler signature); slot 5 family concept explanation (abstract, domain-free). Cross-task concrete code: never. Plus a **vocabulary lock**: post-generation check that the task's domain nouns (from the contract) appear and the *demo's* do not — an early-warning diagnostic, not a pass criterion. Retrieval content is logged per prompt and auditable against the 033 allowlist.

**(d) Measurement.** Slot ablation on dev route tasks: full assembly vs minus-slot variants. **Falsification:** no slot's removal changes route pass rate (retrieval is dead weight beyond the contract); or a governance-approved pilot of concrete sibling examples raises passes while vocabulary-lock violations rise — a gain purchased with copying, non-generalization, disqualified.

**(e) Expected effect: MEDIUM** — plausibly a necessary condition for routes (`LOWER()` alone is pass/fatal), with its effect entangled with the contract's; only the slot ablation can attribute. Evidence currently absent — flagged.

## 7. Iterative testing and integration

**(a) Research basis.** SWE-bench (Jimenez et al. 2024) and SWE-agent (Yang et al. 2024) institutionalized iterative agent workflows — edit → run tests → observe → edit — with the environment as teacher; classic SE practice mirrors it as CI and integration testing (form → API → DB → UI at the pyramid's top). 039's per-case reseed discipline is exactly the deterministic-fixture practice that makes such tests trustworthy.

**(b) Applicability at 0.5B.** Two layers. (i) *Evaluator existence*: react-interaction and fullstack-integration evaluators do not exist (039 explicitly leaves them to Session 040); without them two of six curriculum skills have no oracle and nothing about the model can be concluded — controller infrastructure, not a model technique. (ii) *Iterative install-and-verify as generation strategy* (generate → install → verify → next, own-bytes context) vs generate-all-blind-then-score. Iteration should improve consistency, but the per-piece pipeline already does this partially — the delta is second-order and costs wall-clock and tokens. It cannot touch the model-side gap: React/integration are *long* generations — expect route-style generation-shape failures with more surface area. No evidence exists; both evaluator families are prerequisites for any claim.

**(c) Concrete design.** (i) Build `archagent/s039/harness/react_runner.mjs` (component mounted under jsdom or headless Chromium in the pinned image — decision frozen before any candidate runs; 033's Playwright-against-127.0.0.1 precedent for browser truth) and `harness/integration_runner.mjs` (stages v2 fixtures, runs form→POST→DB→GET→UI-assert with per-case reseed, 10 s probe timeout, single fail-closed verdict). Both inherit `docker_only.py` hardening — digest pin, `--pull never`, network none, read-only root, UID 10001, cap-drop ALL, disclosed exec-tmpfs exception. (ii) Extend the ten-control matrix: React and integration positive controls plus bad controls (wrong keyboard behavior, no-refresh-after-post, swallowed error path), all labeled `TRUSTED_TEACHER_CONTROL_NOT_QWEN_CODE`. (iii) The iteration policy is a Track-D-adjacent ablation at identical budget: install-and-verify ordering vs blind-then-score.

**(d) Measurement.** No baseline exists for the two new families: first establish Track B on them, then the iterate-vs-blind ablation. **Falsification (of iteration):** ordering does not change final pass rates at equal budget — iteration then only moves failure detection earlier (controller/wall-clock benefit). **Falsification (of evaluators):** any control mis-verdict disqualifies that family's numbers (039's 10/10 standard).

**(e) Expected effect: UNKNOWN (mandatory work)** — cannot be estimated honestly before the evaluators exist; the route prior (1/12) suggests integration starts near zero under all tracks.

## 8. Persistent external memory of verified solutions and mistakes

**(a) Research basis.** External memory is the standard answer to agents that retain nothing in weights: Reflexion (Shinn et al. 2023) persists verbal reflections across episodes; Voyager (Wang et al. 2023) accumulates a verified skill library later tasks retrieve and compose; LEAP-style approaches distill recurring mistakes into short principles kept in context. Shared finding: memory helps when entries are *verified* (execution-checked) and *abstracted* (reusable across surface forms).

**(b) Applicability at 0.5B.** Three constraints make this small. (i) *Corpus*: the verified model-origin archive is 22 pieces → 12 normalized structures → 7 families, all in families the model largely solves; the failing families have **zero** verified solutions to memorize (038A §2.2). (ii) *Compliance*: the 033 allowlist admits the model's own previous bytes, concept explanations, and pinned docs — a memory entry is injectable only as an abstracted pattern/principle, not concrete cross-task code, unless governance relaxes the rule. (iii) *Leakage*: holdout is domain-disjoint; memory keyed on domain vocabulary would be training-on-the-test in prompt form. The useful half is the **mistake ledger**: 038A's near-miss taxonomy (demo-vocabulary copying, relation-side optionality, where-construction, prompt-echo degeneracy) converts into family-specific concept warnings — "relation-side optionality must match FK optionality" as a prompt line is memory-of-mistakes in its cheapest, allowlist-clean form. Controller-side; model improvement from it is unmeasured.

**(c) Concrete design.** `experiments/z040-coding-process/memory/ledger.jsonl`, two hash-chained stores: (1) *verified patterns* {family, normalized-structure digest, concept-level pattern text, provenance archive hash, verified_by evaluator id} — derived only from the model's own passing bytes, abstracted to structure not vocabulary; (2) *mistakes* {family, failure class from §5's taxonomy, counterexample, principle text}. Injection: pattern/principle text only, ≤ ~200 tokens, slot 5 of the retrieval assembly, never concrete code, never domain nouns from any non-current domain. Built from train-split archives only, evaluated on dev, frozen before any holdout run; a shuffled-memory control (same length, wrong family) separates content from prompt-length effects.

**(d) Measurement.** Dev with-memory vs without-memory per family, plus the shuffled control and a vocabulary-bleed counter (did memory-conditioned outputs increase wrong-domain nouns?). **Falsification:** with ≤ without on dev; or gains vanish under the shuffled control (length artifact); or vocabulary-bleed increases (memory inducing copying — disqualifying, same logic as demo vocabulary).

**(e) Expected effect: SMALL** — the verified corpus is small, duplicated, and skewed to solved families; the mistake-ledger half is a cheap, plausibly useful controller-side prompt improvement, to be reported as such.

## Cross-cutting: controller-assisted success vs model improvement

**Operational definitions.** *Controller-assisted success*: any pass obtained under a treatment where the deterministic controller contributes information, selection, or iteration beyond the minimal public-contract single-shot prompt (ladders, feedback, retrieval, memory, decomposition) — metric: system-level solve rate (Tracks B/C/D). *Model improvement*: a change in the model-only metric — single-shot pass@1 under the fixed Track-A minimal prompt, same checkpoint, decoding, and seeds per (piece, attempt). **With frozen weights, model improvement is impossible by construction this session**; Track-A movement under prompt deltas is *elicitation* (or leakage), never learning. Session 040 therefore measures the ceiling of controller assistance and produces the residual-gap profile — which families stay at zero under *every* treatment — as the specification for a future weight-level session (the 038A Plan-1 LoRA pilot, separately authorized; no training proposed here).

**Separation mechanics (inherited, non-negotiable):** one checkpoint (sha256 `aff8914e…a47f80`, re-verified after any environment reset — 039's lost-cache lesson); the track-table rules above (identical budgets and seeds, independent final scoring, per-track-and-domain resets, fail-closed verdicts, sealed holdout) apply to every comparison, plus the client regenerated after schema install before route probes (038A staging fix). Prompt-only deltas are the only permitted difference between compared tracks.

**Prompt-leakage audits.** Every prompt delta (B vs A; C's feedback; D's plans; retrieval slots; memory entries) is logged verbatim and audited against the 033 allowlist. Three risks: (i) *solution leakage* — a conventions block or principle encoding a specific dev task's answer inflates all tracks; conventions must be family-general, caught by review; (ii) *demo-vocabulary leakage* — concrete examples must be domain-disjoint from all 16 v2 domains, enforced by the vocabulary lock; (iii) *memory bleed* — train-domain-only, abstracted entries, with the shuffled-memory control separating content from length.

**Attribution.** Every installed byte keeps 033-style attribution (QWEN-ORIGINAL / QWEN-REPAIRED / TEACHER-CORRECTED / TRUSTED-SCAFFOLD); Track C repairs are QWEN-REPAIRED by construction (feedback contains no corrected code); scaffold-fill FIM, if enabled, needs the per-span extension. Model bytes vs teacher bytes reported per track.

**Published metrics:** A single-shot pass@1 (model-only, per skill); B vs A; C repair-attempt efficiency + C vs B + vs budget-matched resampling; D vs B; retrieval slot ablations; with/without memory + shuffled control; iterate-vs-blind; tokens, wall time, peak RSS per track (038A format).

## Prioritized implementation shortlist (expected effect × implementation cost, for THIS session)

1. **Contract-first (Track-B standardization)** — effect LARGE (replicated 4/15 → 9/15), cost ≈ 0 (exists; needs template freeze, conventions block, domain-disjoint demos).
2. **Structured error diagnosis (triage cascade + minimized counterexamples)** — effect MEDIUM, cost LOW (039 evaluators already emit structured fail-closed verdicts; cascade + minimizer + templates are pure controller code).
3. **Execution-feedback-guided repair (Track-C upgrade)** — effect SMALL-to-MEDIUM, cost LOW-MEDIUM (Track R exists; the work is the feedback format and the budget-matched resampling control).
4. **Retrieval of relevant project context (deterministic assembly + vocabulary lock)** — effect MEDIUM, cost MEDIUM (slot design, own-bytes plumbing, ablation harness; no embeddings, no new sandbox surface).
5. **Iterative testing and integration (React + integration evaluators)** — effect UNKNOWN but *mandatory* (two of six v2 skills have no oracle; 039 leaves them to this session); cost HIGH (two runners, extended control matrix, frozen browser-vs-jsdom decision).
6. **Decomposition (Track D)** — effect SMALL/uncertain sign, cost MEDIUM-HIGH (family plan templates, sub-piece install/verify, partitioned budgets).
7. **Persistent external memory (verified patterns + mistake ledger)** — effect SMALL, cost MEDIUM (ledger, abstraction rules, shuffled control; corpus small and skewed to solved families).
8. **Native FIM (insertion-only mode)** — effect SMALL, cost LOW (format change) but negative repair evidence and a governance question (per-span attribution) before scaffold-fill use.

**Top-4 justifications.** *Contract-first* is the only technique with replicated causal evidence at this scale, and every other track is a delta on it — standardizing it (frozen template, `LOWER()` convention, domain-disjoint demos) is near-free and de-risks all comparisons. *Structured error diagnosis* is the cheapest unexploited lever: 038A showed whole pieces lost or spun on verdict-class confusion, and its output (classified, minimized feedback) is exactly what Track C needs — it upgrades an existing null into a fair test at controller-only cost, with benefits controller-side unless first-repair success moves. *Execution-feedback repair* is re-run on v2 to measure the one untested cell — near-miss conversion under minimized counterexamples — with the budget-matched resampling control making the result meaningful either way: if feedback still loses to sampling, the technique is falsified at this scale, and the future training session inherits that as targeting information. *Retrieval* ranks fourth because the route family plausibly lacks information, not just ability (convention, import shape, own schema bytes), the design is deterministic and auditable, and the slot ablation attributes its effect — while its main risk (retrieved concreteness → copying) is exactly what the vocabulary lock measures.

## Known failure modes and harness-defect lessons (and how Session 040 avoids repeating them)

1. **Tri-state verdicts (`bool(None) == False`).** 037's probes returned no-verdict that the controller coerced to fail — a *solved* 251-char invariant was discarded (the misdiagnosed "token cap", refuted by 27–70-token solves). Session 040: every verdict is an explicit enum {pass, fail, no_verdict}; no_verdict halts the loop, logs a harness bug, and never rejects or passes a candidate (038A P1 semantics, inherited by all new runners).
2. **Double-emit verdicts.** 037's fuzz probe emitted two verdict lines and the runner took the last — fuzz enforcement was silently masked in every run. Session 040: single-verdict fail-closed parsing; runners bind the real stdout writer at startup so candidate code cannot suppress or spoof verdicts; duplicate markers → `NO_UNAMBIGUOUS_VERDICT` (039, validated by spoofing-resistance controls).
3. **Demo-vocabulary copying.** `or-stage`: a complete, well-formed predicate in the *demo's* domain words; probes correctly rejected it and feedback could not repair it (dedup spiral). Session 040: demos domain-disjoint from all 16 v2 domains or abstract concept explanations; the vocabulary lock flags wrong-noun outputs early; 039's control matrix already includes a demo-vocabulary copier bad control the oracles reject.
4. **FIM cannot rewrite.** `ma-booking`: a one-character-class semantic fix (missing `?`) FIM micro-repair could not perform (duplicate-flat-stop at 917/2,000 tokens) while blind resampling solved it on attempt 4.
